# Technical Architecture of Spiritty

This document details the engineering choices and internal architecture of **Spiritty**.

---

## 1. Overview & Event Loop

Spiritty relies on an asynchronous event-driven architecture orchestrated by `tokio`. The main thread handles TUI rendering and raw user input capture (`crossterm::event`), while background tasks handle PTY I/O and streaming requests to the LLMs.

```
                    +--------------------------------+
                    |         Keyboard Input         |
                    |   (crossterm::event::Event)    |
                    +---------------+----------------+
                                    |
                                    v
+-------------------+       +---------------+       +--------------------+
|  PTY Reader Task  | ----> |   mpsc Event  | <---- | LLM Streaming Task |
| (Shell Output)    |       |    Channel    |       |  (Tokens & Tools)  |
+-------------------+       +-------+-------+       +--------------------+
                                    |
                                    v
                        +-----------------------+
                        |   Event Loop (App)    |
                        | - State update        |
                        | - Input routing       |
                        +-----------+-----------+
                                    |
                                    v
                        +-----------------------+
                        |  TUI Render (Ratatui) |
                        | - Chat Panel (Left)   |
                        | - Shell Panel (Right) |
                        +-----------------------+
```

## 2. PTY Subsystem & VT100 Emulation

To embed a real terminal inside a Ratatui widget without disturbing the parent shell:

1. **PTY creation (`portable-pty`):**
   - A master/slave pseudo-terminal is allocated.
   - The user's shell (defined by `$SHELL`, e.g. `/bin/zsh`) is instantiated on the slave.
   - Environment variables (`TERM=xterm-256color`, `COLORTERM=truecolor`, etc.) are injected.

2. **Screen emulation (`vt100`):**
   - The raw byte stream generated by the shell (containing ANSI escape codes, cursor movements, colors) is read asynchronously by an I/O thread.
   - These bytes are passed to a `vt100::Parser` instance that maintains a virtual 2D screen in memory.

3. **Rendering in Ratatui:**
   - During the `draw()` rendering pass, the `TerminalPanel` widget reads the cells of the virtual `vt100` screen and converts them into `ratatui::buffer::Buffer` cells (characters, foreground/background colors, bold/underline/reverse attributes).
   - When the interface is resized (split slider or window resize), a `pty.resize(rows, cols)` notification is immediately sent to the slave PTY via `SIGWINCH`.

4. **Split orientation (horizontal / vertical):**
   - The workspace supports two orientations: a **horizontal** split (chat on top / terminal at the bottom — the default at ~70% chat height, suited to narrow terminals) and a **vertical** split (chat left / terminal right). `F4` toggles between them.
   - Each orientation keeps its own ratio (`split_ratio` for vertical, `split_ratio_horizontal` for horizontal), persisted in `~/.config/spiritty/config.toml`. Mouse dragging and `Alt + ←/→` (vertical) or `Alt + ↑/↓` (horizontal) adjust the active ratio; the PTY is resized automatically whenever the terminal panel's inner area changes, so both orientations stay accurate.

## 3. AI Agent System & Context Injection

### 3.1. System Context Extractor (`system::Context`)
Before sending a prompt to the LLM, the agent dynamically enriches the request with host metadata:
- **OS / Distribution:** Detected via `/etc/os-release` (e.g. Ubuntu 24.04, Arch Linux, Fedora 40, macOS Sonoma).
- **Package managers:** Presence of `apt`, `pacman`, `dnf`, `zypper`, `brew`, `nix`, `cargo`, `pip`, etc.
- **Shell environment:** Shell name, current directory (`$PWD`), current user (`whoami`, root or not).
- **Last execution context:** Recent outputs and error codes (`$?`) from the terminal panel.

### 3.2. Prompts & Roles
The agent uses a specialized `System Prompt` instructing it to act as an expert in system administration and the command line:
- Concise answers (suited to the terminal format).
- Favor exact, modern commands (e.g. `ss` over `netstat`, `ip` over `ifconfig`, `rg` over `grep`).
- Structure actions as executable command blocks with an explicit risk level.

---

## 4. Security & Human-in-the-Loop (Command Validation)

The agent never types directly into the shell without control:

1. **Action proposal:** The agent produces a command with a short justification.
2. **Criticality analysis (risk heuristic, `CommandRisk`):**
   - 🟢 **Safe (Read-only):** `cat`, `ls`, `grep`, `systemctl status`, `df -h`
   - 🟡 **Standard (Local modification):** `touch`, `mkdir`, `git commit`, `cargo build`
   - 🟣 **Sudo (Legitimate non-destructive elevation):** benign elevated commands (e.g. `sudo systemctl status`), eligible for auto-approval at the `Sudo` level.
   - 🔴 **Risky (System impact / destructive):** `sudo rm -rf`, `dd`, `mkfs`, `iptables`, `systemctl restart` — manual validation mandatory outside YOLO mode.
3. **User control:**
   - `[Alt + 1..9]`: Directly runs command proposal N.
   - `[F10]` / `[Enter]` (empty input field): Approves the command awaiting authorization.
   - `[Esc]`: Rejects the proposal and informs the agent.
   - The active auto-approval level (`F3`: 🟢 Safe / 🟡 Sudo / 🔴 YOLO / ⚫ Off) decides whether an eligible proposal is injected automatically into the PTY; a safeguard bounds consecutive automatic chains.

## 5. Multi-Provider LLM Abstraction

Spiritty implements a unified trait for communicating with models:

```rust
#[async_trait]
pub trait LlmProvider: Send + Sync {
    async fn stream_completion(
        &self,
        messages: &[ChatMessage],
        context: &SystemContext,
        event_sender: mpsc::UnboundedSender<AgentEvent>,
    ) -> Result<()>;
}
```

### Implemented Providers:
1. **Ollama:** Local HTTP API (`http://localhost:11434/api/chat`), zero external dependency, direct streaming, ideal in a disconnected environment.
2. **Google Gemini:** Native REST API (Interactions / GenerateContent) via `reqwest` for minimal latency and extended context windows.
3. **Anthropic Claude:** Claude 3.5 Sonnet / Haiku support for complex system reasoning.
4. **OpenAI-compatible (`v1/chat/completions`):** OpenAI, DeepSeek, xAI Grok, Z.ai/GLM, LM Studio. Any brand in the OpenAI format goes through `providers/openai.rs` (do not create one file per brand); "reasoning" models there fold `reasoning_content` into `<think>…</think>` blocks.

## 6. Internationalization (i18n) Engine

Spiritty natively supports multiple languages (French, English) at the level of the TUI interface and the agent instructions:

1. **Language Detection & Configuration:**
   - Priority order: User configuration (`~/.config/spiritty/config.toml` -> `language = "fr" | "en"`) > Environment variable (`$LC_ALL`, `$LC_MESSAGES`, `$LANG`) > Fallback **French** (`fr`, see `Language::detect_system()` in `src/i18n/mod.rs`).
2. **Compile-Time Typed Translation Catalog:**
   - A catalog based on an `I18nKey` enum guarantees 100% at `cargo check` time that no translation string is missing or orphaned.
   - Ultra-fast access via static pointer matching (`&'static str`), with no runtime parsing of JSON or PO files.
3. **Localization of System Prompts:**
   - The AI agent adapts its conversation language and explanation wording to the configured language while preserving technical terms and exact commands.

---

## 7. Error Handling & Robustness

- All I/O errors (dead PTY, LLM timeout, corrupted configuration file) are turned into typed `AppEvent::Error` events or displayed in the status bar without crashing the application.
- Panic hooks immediately restore the terminal's raw mode so as not to corrupt the user's shell.

---

## 8. Session Persistence & Context Compaction

Spiritty includes a complete session manager and context-memory optimizer:

1. **Structured JSON Storage (`~/.config/spiritty/sessions/<id>.json`):**
   - Automatic persistence of the full message history (`User`, `Assistant`, `System`).
   - Saving of the user prompt history (`prompt_history`), allowing immediate restoration of navigation with `▲ / ▼`.
   - Complete metadata: timestamp, total tokens consumed, associated model and provider, title automatically inferred from the first question.
2. **Request-Time Context Compaction (`compact_chat_messages()`):**
   - The session JSON keeps the **entire** history: since v0.5.2, `save_current_session` no longer compacts anything; reloading and scrolling restore every exchange (no more "1 summary + recent turns" cap in the session list).
   - Compaction applies **only to the context sent to the LLM**, at request time (`agent::send_prompt`). Beyond **8** messages, older turns roll into a single `System` structured summary message (executed `💻` commands, key points) while the **8** most recent are kept verbatim; a conversation of 8 messages or fewer is transmitted as-is (large messages remain bounded).
   - `compact_chat_messages` is a **pure** transformation: it mutates neither the live conversation nor the persisted session. `Session::compact()` is kept only for compatibility with older callers/tests.
3. **Strict Jinja / LLM Template Compatibility:**
   - To respect the strict invariant of Hugging Face / Qwen / Llama 3 models (`System message must be at the beginning`), archived context messages are transmitted with the `user` role in streaming API requests, avoiding any HTTP 500 crash.
